## 1. "무겁다"를 분해하기 — 범인은 삼각형만이 아니다

Day 12에서 STEP과 IFC를 손에 넣었다고 합시다. 그대로 Unity에 던지면 대개 이런 일이 벌어집니다.

- 임포트에 40분이 걸리고, 에디터가 중간에 한 번 죽습니다
- 띄우고 나면 6fps가 나옵니다
- 빌드 용량이 2.8GB가 됩니다

여기서 반사적으로 "폴리곤을 줄이자"로 가는 게 가장 흔한 실수입니다. 실시간 성능을 잡아먹는 요인은 넷이고, 각각 해법이 완전히 다릅니다.

| 요인 | 증상 | 전형적인 원인 | 해법 |
|---|---|---|---|
| **삼각형 수** | GPU 바운드, 해상도 올리면 더 느려짐 | CAD 테셀레이션 과다 | 테셀레이션 제어, 데시메이션 |
| **드로우콜 / 머티리얼** | CPU 바운드, 해상도와 무관하게 느림 | 부품 4만 개가 각각 별도 오브젝트 | 병합, 인스턴싱, 머티리얼 통합 |
| **노드(오브젝트) 수** | 임포트·씬 로딩이 지옥, 에디터가 버벅임 | CAD 어셈블리 트리 전체 보존 | 계층 평탄화, 불필요 부품 제거 |
| **텍스처 메모리** | VRAM 초과, 모바일/WebGL에서 크래시 | 4K PNG 수백 장 | KTX2/Basis 압축, 해상도 하향 |

CAD에서 온 트윈은 대부분 **두 번째와 세 번째**에 먼저 막힙니다. 볼트 하나하나가 독립 GameObject이고 각자 머티리얼을 들고 있으면, 삼각형이 총 50만 개밖에 안 돼도 드로우콜 4만 개 때문에 프레임이 나오지 않습니다. 반대로 스캔 메시는 노드가 하나뿐이지만 삼각형이 3천만 개라 첫 번째에 막힙니다.

> 💡 **실무 팁**: 경량화를 시작하기 전에 원본의 수치를 **반드시 먼저 집계**하세요. 삼각형 수, 노드 수, 고유 머티리얼 수, 텍스처 총 용량 네 가지입니다. 이걸 모르고 작업하면 "뭔가 줄였는데 여전히 느리다"는 상태에서 며칠을 보냅니다. 숫자를 보면 어디를 손댈지가 5분 만에 정해집니다.

### 예산 먼저, 작업은 그다음

Day 12에서 "폴리곤 예산을 먼저 정하라"고 했던 그 숫자를 여기서 씁니다. 타깃 플랫폼별로 현실적인 기준은 대략 이렇습니다.

| 타깃 | 삼각형(씬 전체) | 드로우콜 | 텍스처 메모리 |
|---|---|---|---|
| 데스크톱 PC | 300만~800만 | ~2,000 | 1~2GB |
| WebGL (Day 38) | 50만~150만 | ~500 | 200~400MB |
| 모바일 / 태블릿 | 30만~100만 | ~300 | 150~300MB |
| VR (90fps 유지) | 100만~200만 | ~500 | 500MB |

이 수치를 설비 대수로 나누면 **설비 1대당 목표치**가 나옵니다. 설비 20대를 WebGL로 띄운다면 1대당 삼각형 3만 개, 드로우콜 10개 수준입니다. 원본이 1대당 120만 개라면 40분의 1로 줄여야 한다는 뜻이고, 이건 "데시메이션 좀 돌리면 되겠지"로 될 숫자가 아닙니다. **부품의 90%를 삭제해야 도달하는 숫자**입니다. 이 인식 차이가 경량화 작업의 성패를 가릅니다.

## 2. STEP → 메시 — 변환은 "자르기"가 9할

STEP은 B-Rep이므로(Day 12) 테셀레이션을 거쳐야 메시가 됩니다. 순서가 중요합니다.

```
STEP 원본
  │
  ① 부품 솎아내기  ← 여기서 70~90%가 사라진다. 가장 큰 효과.
  │
  ② 테셀레이션     ← 현 편차 설정. 여기서 삼각형 수가 결정된다.
  │
  ③ 메시 정리      ← 병합, 인스턴싱, 머티리얼 통합
  │
  ④ glTF 익스포트
  │
  ⑤ 압축           ← Draco / 양자화 / KTX2
```

**①을 건너뛰고 ⑤부터 하려는 시도가 가장 흔한 실패 패턴입니다.** Draco로 70%를 줄여 봐야, 애초에 안 보이는 내부 기어를 들고 있으면 의미가 없습니다. 없애는 게 줄이는 것보다 항상 낫습니다.

### ① 부품 솎아내기 — 무엇을 지울 것인가

CAD 어셈블리에서 지워도 되는 것들은 패턴이 뚜렷합니다.

- **체결 부품**: 볼트, 너트, 와셔, 핀, 리벳. 이름이나 부품 번호로 일괄 선택이 가능한 경우가 많습니다. 나사산 하나가 삼각형 2,000개입니다
- **커버 안쪽**: 외부 케이싱을 열지 않을 거라면 내부 기어·베어링·배선은 전부 불필요합니다
- **치수가 작은 것**: 바운딩 박스 대각선이 5mm 미만인 부품은 1m 거리에서 보이지 않습니다. 자동 필터링하기 좋은 기준입니다
- **중복 인스턴스**: 같은 부품이 200개 반복되면 메시 하나 + 트랜스폼 200개로 바꿉니다(인스턴싱)

실무에서는 CAD 도구(FreeCAD, SolidWorks, CATIA 등)나 전용 변환 도구의 필터 기능을 씁니다. 크기 기준 자동 필터는 이런 식으로 동작합니다.

```
규칙 예시 (프레스 설비 1대 기준)
  - 이름이 "BOLT_*", "NUT_*", "WASHER_*" 인 부품 → 삭제     (−12,400개)
  - 바운딩 박스 대각선 < 8mm                     → 삭제     (− 3,100개)
  - "COVER_MAIN" 내부에 완전히 포함된 부품        → 삭제     (− 2,800개)
  - 동일 형상 반복 200개                          → 인스턴스화

  결과: 부품 21,000개 → 1,900개 (−91%)
        삼각형 1,180만 → 86만    (−93%)
```

> 💡 **실무 팁**: 지우기 전에 **"이 부품에 센서가 붙을 일이 있는가"**를 Day 11의 태그맵과 대조하세요. 모터 하우징은 안 보여도 온도 센서의 바인딩 대상일 수 있습니다. 보이지 않지만 이름이 필요한 노드는, 메시를 지우고 **빈 노드(이름만 있는 트랜스폼)로 남겨 두면** 용량 비용 없이 바인딩 지점을 보존할 수 있습니다.

### ② 테셀레이션 — 현 편차 하나가 전부를 바꾼다

Day 12에서 봤듯 현 편차(chord deviation)가 삼각형 수를 지배합니다. 트윈에서의 현실적인 기준은 **"관찰 거리"로 정하는 것**입니다.

| 관찰 거리 | 현 편차 | 각도 허용치 | 쓰임새 |
|---|---|---|---|
| 0.3m (손으로 만지는 거리) | 0.05mm | 5° | VR 정비 훈련, 부품 상세 뷰 |
| 1~2m (설비 앞에 선 거리) | 0.5mm | 15° | 일반 설비 모델 |
| 5~10m (라인 전체 조망) | 2mm | 30° | 배경 설비, 프록시 |

기본값은 대개 0.01~0.05mm로 잡혀 있어 1~2m 기준보다 **10배 이상 조밀합니다.** 이 값만 0.5mm로 바꿔도 삼각형이 보통 5~15배 줄고, 화면상 차이는 보이지 않습니다. 경량화 작업 중 **투입 시간 대비 효과가 가장 큰 단일 설정**입니다.

## 3. IFC → glTF — 솎아내기는 "공간과 타입"으로

IFC는 성격이 반대입니다. B-Rep도 섞여 있지만 상당수는 이미 압출(extrusion) 기반이고, 진짜 문제는 **객체 수**입니다. 건물 하나에 `IfcWall` 1만 2천 개, 전체 수십만 객체는 흔합니다.

IFC 솎아내기의 축은 둘입니다. **층·구역으로 자르기**와 **타입으로 거르기**입니다. `ifcopenshell`로 처리하는 게 가장 편합니다.

```python
import ifcopenshell

model = ifcopenshell.open("plant.ifc")

# 1) 타입별 개수 집계 — 규모 파악이 먼저 (Day 12의 그 작업)
from collections import Counter
counts = Counter(e.is_a() for e in model)
for t, n in counts.most_common(15):
    print(f"{t:30s} {n:>7,}")

# 2) 트윈 대상 층만 남기기
TARGET_STOREY = "B1 기계실층"
storeys = {s.Name: s for s in model.by_type("IfcBuildingStorey")}
target = storeys[TARGET_STOREY]

# 3) 트윈에 필요 없는 타입 목록 (프로젝트마다 다르게 정한다)
DROP_TYPES = {
    "IfcFurnishingElement",   # 가구
    "IfcAnnotation",          # 주석·치수선
    "IfcGrid",                # 설계 그리드
    "IfcOpeningElement",      # 개구부 (형상 불필요)
    "IfcReinforcingBar",      # 철근 — 개수는 압도적이고 보이지 않는다
}

keep = [
    e for e in model.by_type("IfcProduct")
    if e.is_a() not in DROP_TYPES
]
print(f"남는 객체: {len(keep):,}")
```

`IfcReinforcingBar`는 특히 주의할 타입입니다. 구조 모델에서는 철근이 전체 객체의 절반을 넘기도 하는데, 트윈에서는 단 한 번도 보이지 않습니다.

### IFC 변환에서 반드시 지켜야 할 것 — GlobalId

Day 12에서 봤듯 IFC의 `GlobalId`는 Day 16 자산 트리의 ID로 쓸 자산입니다. **변환 과정에서 이게 날아가면 BIM을 쓴 의미의 절반이 사라집니다.** glTF에는 노드마다 `extras` 필드에 임의 JSON을 넣을 수 있으므로 여기에 실어 보냅니다.

```json
{
  "nodes": [
    {
      "name": "AHU-01",
      "mesh": 42,
      "extras": {
        "ifcGlobalId": "2O2Fr$t4X7Zf8NOew3FLKU",
        "ifcType": "IfcFlowTerminal",
        "storey": "B1",
        "assetTag": "AHU-B1-01"
      }
    }
  ]
}
```

Unity에서 glTF를 읽을 때 `extras`를 함께 파싱해 두면(Day 18), Day 20의 데이터 바인딩에서 "설비 태그 → 3D 노드"를 이름 문자열 매칭이 아니라 **ID 매칭**으로 처리할 수 있습니다. 이름은 변환 과정에서 `AHU-01`이 `AHU-01_mesh_003`으로 바뀌는 일이 흔하지만, `extras`는 그대로 살아남습니다.

> 💡 **실무 팁**: 변환 도구가 `extras`를 지원하지 않는다면, 변환 후 **별도의 매핑 JSON을 따로 내보내세요.** `{ "노드이름": { "globalId": ..., "tag": ... } }` 형태 한 장이면 충분합니다. 3D 파일과 메타데이터를 분리해서 들고 가는 건 전혀 나쁜 설계가 아니고, 오히려 메타데이터만 갱신할 때 편합니다.

## 4. 메시 단계 경량화 — 데시메이션보다 먼저 할 것들

부품을 솎아내고 테셀레이션을 잡았는데도 예산을 못 맞췄다면 이제 메시를 손댑니다. 순서는 **효과가 크고 품질 손실이 적은 것부터**입니다.

### ① 인스턴싱 — 손실 0, 효과 큼

같은 형상이 반복되면 메시 데이터는 하나만 두고 트랜스폼만 N개 둡니다. 컨베이어 롤러 400개, 동일 모터 12대, 같은 조명 기구 80개 — CAD 어셈블리에는 이런 게 널려 있습니다. glTF는 노드가 같은 `mesh` 인덱스를 참조하면 자연히 인스턴스가 되고, `EXT_mesh_gpu_instancing` 확장을 쓰면 GPU 인스턴싱까지 갑니다. **품질 손실이 전혀 없으면서 용량과 드로우콜을 동시에 줄이는 유일한 수단**이라, 가장 먼저 해야 합니다.

### ② 병합(merge) — 드로우콜을 줄인다

반대로, 개별 제어가 필요 없는 부품들은 **하나로 합칩니다.** 안전 펜스 120개 패널을 각각 선택할 일이 없다면 하나의 메시로 병합합니다. 드로우콜 120 → 1입니다.

판단 기준은 명확합니다. **"이 오브젝트를 따로 선택하거나, 따로 색을 바꾸거나, 따로 움직일 일이 있는가?"** 하나라도 예면 분리 유지, 전부 아니오면 병합입니다. 이 질문의 답은 Day 22(오브젝트 피킹)와 Day 23(경보 시각화) 설계에서 나옵니다. **그래서 경량화는 화면 설계가 어느 정도 정해진 뒤에 하는 게 맞습니다.**

### ③ 데시메이션 — 마지막 수단

삼각형을 실제로 줄이는 단계입니다. Blender의 Decimate 모디파이어나 meshoptimizer의 simplifier를 씁니다. 주의점이 있습니다.

- **기계 부품에는 잘 안 듣습니다.** 데시메이션은 곡면이 많은 유기적 형상에 강하고, 평면과 직각 모서리로 된 기계 부품은 50%만 줄여도 모서리가 뭉개집니다. 기계류는 데시메이션보다 **테셀레이션 재설정**이 거의 항상 낫습니다(원본 B-Rep이 있다면)
- **스캔 메시에는 아주 잘 듣습니다.** 포토그래메트리 결과물은 90% 줄여도 텍스처가 디테일을 유지해 줍니다(Day 14)
- **UV와 노멀을 깨뜨립니다.** 텍스처가 있는 메시는 데시메이션 후 UV 왜곡을 반드시 확인하세요

### ④ LOD — 거리에 따라 바꿔 끼우기

경량화의 다른 축은 **상황에 따라 다른 모델을 쓰는 것**입니다. 가까이 가면 상세 모델, 멀어지면 프록시로 전환합니다. Unity는 LODGroup으로 처리합니다.

트윈에서 특히 효과적인 이유는, 공장 트윈의 카메라가 대부분 시간을 **전체 조망 위치**에서 보내기 때문입니다. 설비 20대 중 19대는 항상 멀리 있습니다. LOD2(프록시)를 삼각형 2천 개로 만들어 두면, 조망 상태의 씬 전체가 갑자기 가벼워집니다.

```
설비 1대의 LOD 구성 예
  LOD0  화면 비중 > 30%   삼각형 86,000   부품 분리 유지 (피킹·색상 변경 대상)
  LOD1  화면 비중 > 8%    삼각형 18,000   주요 부품만 분리, 나머지 병합
  LOD2  화면 비중 > 2%    삼각형  2,100   단일 메시, 단일 머티리얼
  컬링  그 이하            렌더링 안 함
```

## 5. glTF 단계 압축 — Draco, 양자화, KTX2

여기까지 오면 구조는 정리됐습니다. 마지막은 **같은 형상을 더 작은 바이트로 담는** 단계입니다. 세 가지가 있고, 성격이 다릅니다.

| 기법 | 줄이는 것 | 손실 | 런타임 비용 | 적용 대상 |
|---|---|---|---|---|
| **Draco** | 파일 용량(지오메트리) | 설정에 따라 유손실 | 디코딩 CPU 시간 발생 | 다운로드가 병목일 때 |
| **메시 양자화** (`KHR_mesh_quantization`) | 파일 + **GPU 메모리** | 비트 수에 따라 유손실 | 거의 없음 | 거의 항상 |
| **KTX2 / Basis** (`KHR_texture_basisu`) | 텍스처 파일 + **VRAM** | 유손실 | 없음 (GPU 네이티브) | 텍스처가 있으면 항상 |

세 가지의 차이를 정확히 알아야 선택이 됩니다.

**Draco**는 압축률이 매우 높습니다(지오메트리 70~90% 감소). 하지만 **GPU에 올라가는 순간 압축이 풀립니다.** 즉 VRAM은 전혀 줄지 않고, 로딩 시 디코딩 시간이 추가됩니다. 네트워크로 받아 오는 WebGL 트윈(Day 38)에서는 결정적이지만, 로컬 데스크톱 빌드에서는 오히려 로딩이 느려질 수 있습니다.

**메시 양자화**는 위치·노멀·UV를 float32 대신 int16/int8로 저장합니다. 압축률은 Draco보다 낮지만(50~70%) **GPU 메모리에서도 그대로 작은 상태로 유지**되고, 디코딩 비용이 사실상 없습니다. 기본으로 켜 두기 좋은 쪽입니다.

> 💡 **실무 팁**: 양자화 비트 수를 정할 때는 **모델의 물리적 크기를 함께 보세요.** 위치를 14비트로 양자화하면 바운딩 박스를 16,384 단계로 나눈 해상도가 됩니다. 10m짜리 설비라면 0.6mm 격자 — 충분합니다. 하지만 공장 전체 200m를 한 메시에 담고 14비트를 쓰면 격자가 12mm가 되어 작은 부품이 울퉁불퉁해집니다. **설비 단위로 파일을 쪼개면 이 문제가 자동으로 해결됩니다.**

### 실제 명령

`gltfpack`(meshoptimizer)과 `gltf-pipeline`(Cesium)이 사실상 표준 CLI입니다. 파이프라인에 넣기 좋습니다.

```bash
# gltfpack: 양자화 + 메시 최적화 + 텍스처 KTX2 (데스크톱/WebGL 공통 권장 조합)
gltfpack -i press_line.gltf -o press_line_opt.glb \
         -cc \            # 메시 최적화 + 양자화 (compress 모드)
         -tc \            # 텍스처를 KTX2(Basis)로 변환
         -si 0.5 \        # 삼각형을 50%로 단순화 (생략 가능)
         -kn -km          # 노드 이름 / 머티리얼 이름 유지 ← 트윈에서는 필수

# gltf-pipeline: Draco 압축 (네트워크 다운로드가 병목인 WebGL 배포용)
gltf-pipeline -i press_line_opt.glb -o press_line_draco.glb \
              --draco.compressionLevel 7 \
              --draco.quantizePositionBits 14
```

`-kn -km`(이름 유지)을 빼먹는 실수가 자주 나옵니다. 최적화 도구들은 기본적으로 이름을 버려서 용량을 줄이는데, 트윈에서는 **노드 이름이 바인딩 키**라 이름이 사라지면 Day 20에서 아무것도 붙일 수 없습니다. 압축률 2%를 아끼려다 파이프라인 전체를 다시 돌리게 됩니다.

### 숫자로 보는 누적 효과

프레스 라인 설비 5대 기준의 전형적인 진행입니다.

| 단계 | 삼각형 | 노드 | 파일 크기 |
|---|---|---|---|
| STEP 원본 (기본 설정 변환) | 5,900만 | 104,000 | 2,100 MB |
| ① 부품 솎아내기 | 740만 | 9,500 | 310 MB |
| ② 테셀레이션 재설정 (0.5mm) | 310만 | 9,500 | 128 MB |
| ③ 인스턴싱 + 병합 | 310만 | 1,800 | 71 MB |
| ④ 양자화 + KTX2 (`gltfpack -cc -tc`) | 310만 | 1,800 | 19 MB |
| ⑤ Draco (WebGL 배포용) | 310만 | 1,800 | 7 MB |

눈여겨볼 지점은 **①과 ②에서 전체 감소의 94%가 일어났다**는 것입니다. 압축 도구는 마지막 마무리일 뿐입니다. 많은 팀이 ①②를 건너뛰고 ④⑤만 돌린 뒤 "glTF 압축해도 여전히 느리다"고 말하는데, 당연한 결과입니다. 압축은 드로우콜도 노드 수도 줄이지 않습니다.

## 6. 파이프라인으로 만들기 — 한 번 하고 끝이 아니다

설비 모델은 갱신됩니다. 제조사가 개정 도면을 보내고, 라인에 설비가 추가되고, 스캔을 다시 뜹니다. 그때마다 사람이 GUI에서 30단계를 반복하면 **두 번째부터 안 합니다.** 그래서 경량화는 처음부터 스크립트로 짜 두는 게 맞습니다.

```
assets/
  source/              # 원본 — 절대 수정하지 않는다 (버전 관리 대상)
    press_01.step
    plant_b1.ifc
  rules/
    press_01.yaml      # 솎아내기 규칙, 테셀레이션 값, 예산
  build/               # 생성물 — git에 넣지 않는다
    press_01.glb
    press_01.map.json  # 노드 ↔ 자산 태그 매핑
```

규칙 파일은 이런 모양이면 충분합니다.

```yaml
# rules/press_01.yaml
source: press_01.step
tessellation:
  chord_deviation_mm: 0.5
  angle_tolerance_deg: 15
drop:
  name_patterns: ["BOLT_*", "NUT_*", "WASHER_*", "PIN_*"]
  min_bbox_diagonal_mm: 8
  inside_of: ["COVER_MAIN", "COVER_REAR"]
keep_as_empty:          # 메시는 지우되 바인딩용 노드는 남긴다
  - "MOTOR_01_HOUSING"
  - "GEARBOX_MAIN"
budget:
  max_triangles: 90000
  max_draw_calls: 24
pack:
  quantize: true
  textures_ktx2: true
  keep_names: true
```

### 검증 — 자동화의 핵심은 체크다

파이프라인에 **빌드 실패 조건**을 넣어 두면 품질이 저절로 유지됩니다. 최소 네 가지는 검사할 만합니다.

1. **예산 초과**: 삼각형·드로우콜이 `budget`을 넘으면 빌드 실패
2. **바인딩 키 누락**: Day 11의 태그맵에 있는 모든 태그가 glTF 노드(또는 `extras`)에서 찾아지는지 확인. 하나라도 없으면 실패
3. **바운딩 박스 급변**: 직전 빌드 대비 크기가 10% 이상 달라졌으면 단위 오류를 의심(Day 15)
4. **시각적 회귀**: 고정 카메라에서 렌더링한 스냅샷을 직전 빌드와 픽셀 비교. 차이가 크면 사람이 확인

2번이 특히 중요합니다. 경량화 과정에서 조용히 사라진 노드는 Unity에 올려 보기 전까지 드러나지 않고, 보통 **발표 전날에 "모터 온도가 왜 안 뜨죠"로 발견**됩니다.

> 💡 **실무 팁**: `source/`의 원본은 **절대 덮어쓰지 마세요.** 경량화는 항상 원본 → 생성물 방향의 단방향 변환이어야 합니다. 원본을 직접 수정해 가며 줄이기 시작하면, 두 달 뒤 "LOD0를 좀 더 상세하게 뽑아야 한다"는 요구가 왔을 때 돌아갈 곳이 없습니다. 디스크는 쌉니다.

## 📝 핵심 요약

1. "무겁다"는 삼각형 수·드로우콜·노드 수·텍스처 메모리 네 가지로 분해된다. CAD 기반 트윈은 보통 드로우콜과 노드 수에 먼저 막히므로, 삼각형부터 줄이려 들면 시간만 쓰고 프레임은 그대로다. 작업 전에 네 수치를 집계하고 플랫폼별 예산과 대조하는 게 먼저다.
2. 경량화 효과의 90% 이상은 **부품 솎아내기와 테셀레이션 재설정**에서 나온다. 체결 부품·내부 부품·미소 부품을 규칙으로 일괄 삭제하고, 현 편차를 관찰 거리에 맞춰(일반 설비는 0.5mm) 다시 잡는 것만으로 삼각형이 한 자릿수 퍼센트까지 떨어진다.
3. IFC는 **공간(층·구역)과 타입**으로 자른다. `IfcReinforcingBar` 같은 보이지 않는 대량 타입이 객체의 절반을 차지하는 일이 흔하다. 자를 때 `GlobalId`를 glTF `extras`나 별도 매핑 JSON으로 반드시 보존해야 Day 16·20의 바인딩이 ID 기반으로 성립한다.
4. 압축 세 가지는 역할이 다르다. Draco는 파일만 줄이고 VRAM은 안 줄이며 디코딩 비용이 붙는다(네트워크 병목용). 메시 양자화는 GPU 메모리까지 줄이고 비용이 없어 기본으로 켤 만하다. 텍스처는 KTX2/Basis가 VRAM에서 압축 상태를 유지하는 유일한 선택지다. 어느 도구를 쓰든 **노드·머티리얼 이름 유지 옵션은 필수**다.
5. 경량화는 일회성 작업이 아니라 원본 → 생성물 단방향 파이프라인으로 짜고, 예산 초과·바인딩 키 누락·바운딩 박스 급변을 빌드 실패 조건으로 걸어 둔다. 원본은 절대 덮어쓰지 않는다.
