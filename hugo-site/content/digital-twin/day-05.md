## 1. 왜 코드보다 문서가 먼저인가

Phase 2부터는 손을 움직입니다. MQTT 브로커를 띄우고, OPC UA 서버에 붙고, 시계열 DB에 값을 꽂습니다. 그런데 그 작업을 시작하는 순간 **되돌리기 어려운 결정들이 조용히 고정됩니다.** 토픽 이름 규칙, 샘플링 주기, 설비 식별자 체계, 타임스탬프의 주인 — Day 04에서 봤듯이 이것들은 나중에 바꾸면 그동안 쌓인 데이터가 전부 쓸모없어집니다.

범위 정의서는 거창한 산출물이 아닙니다. **A4 두 장 분량으로, 되돌리기 어려운 결정만 미리 적어두는 문서**입니다. 목적은 둘입니다.

1. 나중에 "그때 왜 이렇게 했지?"에 답하기 위한 기록
2. 요구가 늘어날 때 "그건 이 범위 밖입니다"라고 가리킬 수 있는 기준선

특히 2번이 중요합니다. 디지털 트윈 프로젝트는 데모가 성공할수록 요구가 번집니다. 설비 3대짜리 트윈이 잘 돌아가면 다음 주에 "공장 전체"가 되고, 그다음에는 "다른 공장도"가 됩니다. 범위가 문서에 못 박혀 있지 않으면 거절할 근거가 없습니다.

> 💡 **실무 팁**: 이 문서는 한 번 쓰고 끝내는 게 아니라 Phase가 끝날 때마다 다시 꺼내 고칩니다. 바뀐 항목에는 **바꾼 날짜와 이유**를 남기세요. 나중에 돌아볼 때 결정 자체보다 그 이유가 훨씬 유용합니다.

## 3. 항목 1–3: 목적과 경계 정하기

### 의사결정부터 거꾸로 쓴다

가장 흔한 실패는 1번 항목을 "설비 상태를 실시간으로 모니터링한다"로 쓰는 것입니다. 이건 목적이 아니라 수단입니다. 모니터링해서 **누가 무엇을 다르게 하는지**가 빠져 있습니다.

쓸 만한 형태는 이렇습니다.

```
나쁜 예:  프레스 설비의 상태를 3D로 시각화한다.
좋은 예:  야간 당직자가 프레스 3호기의 과열 징후를 현장 순회 없이
         15분 이내에 인지하고, 라인 정지 여부를 스스로 판단한다.
```

좋은 예에는 **행위자(야간 당직자)**, **판단(라인 정지 여부)**, **현재와의 차이(현장 순회 없이, 15분 이내)** 가 모두 들어 있습니다. 이 문장이 써지면 나머지 항목이 거의 자동으로 결정됩니다. 15분 이내 인지가 목표라면 1초 샘플링은 과하고, 라인 정지 판단이 목표라면 온도 하나로는 부족하다는 게 바로 드러납니다.

### 범위는 "밖"을 쓸 때 비로소 생긴다

2번 항목에서 안쪽만 적으면 경계가 생기지 않습니다. 반드시 Out of scope를 같은 분량으로 씁니다.

```
In scope   : 1라인 프레스 3대 (P-01, P-02, P-03), 해당 구역 실내 환경
Out of scope: 2·3라인 / 상위 MES·ERP 연동 / 설비 제어(쓰기) /
             모바일 앱 / 외부 협력사 계정
```

여기서 **"설비 제어(쓰기)"를 범위 밖으로 선언한 것**이 가장 중요한 한 줄입니다. Day 04에서 봤듯이 역방향 경로가 생기는 순간 시스템의 성격이 바뀌고 보안·안전 요구가 몇 배로 뜁니다. 1차 릴리스를 **읽기 전용으로 못 박는 것**이 거의 항상 옳은 선택입니다.

### 성숙도 목표는 한 단계만 올린다

Day 02의 5단계(서술 → 정보 → 예측 → 처방 → 자율)에서, 1차 릴리스 목표는 **현재보다 정확히 한 단계 위**로 잡습니다.

| 현재 상태 | 1차 목표 | 하지 말아야 할 것 |
|---|---|---|
| 아무것도 없음 | 2단계(정보): 실시간 상태 + 이력 조회 | 처음부터 고장 예측 모델 |
| 대시보드는 있음 | 3단계(예측): 이상 탐지와 추세 경고 | 자동 제어 |
| 예측까지 됨 | 4단계(처방): 조치 추천 | 사람 없는 자율 루프 |

두 단계를 한 번에 뛰려는 프로젝트가 실패하는 이유는 기술이 어려워서가 아니라 **아래 단계의 데이터 품질이 검증되지 않은 채 위를 쌓기 때문**입니다. 센서 결측률이 20%인 상태에서 만든 예측 모델은 모델이 틀린 건지 데이터가 틀린 건지조차 구분할 수 없습니다.

## 4. 항목 4–5: 데이터와 모델의 범위를 표로 고정하기

### 데이터 인벤토리 — 가장 많은 시간을 아껴주는 표

4번 항목은 산문으로 쓰지 말고 표로 씁니다. 이 표 하나가 Phase 2 전체의 작업 지시서가 됩니다.

| 태그 | 설비 | 물리량 | 주기 | 출처/프로토콜 | 보존 | 이 값으로 내리는 판단 |
|---|---|---|---|---|---|---|
| `P01.temp.die` | P-01 | 금형 온도 (°C) | 1초 | PLC / Modbus TCP | 원본 7일 → 1분 평균 1년 | 과열 경보 |
| `P01.vib.rms` | P-01 | 진동 RMS (mm/s) | 100ms | 진동 센서 / MQTT | 원본 3일 → 1분 통계 1년 | 베어링 이상 징후 |
| `P01.current` | P-01 | 주모터 전류 (A) | 1초 | PLC / Modbus TCP | 원본 7일 → 1분 평균 1년 | 부하 이상, 가동 여부 |
| `ZONE1.temp` | 구역 | 실내 온도 (°C) | 5분 | IoT 센서 / MQTT | 원본 1년 | 환경 보정값 |

맨 오른쪽 칸이 Day 04에서 말한 자가 진단입니다. **"이 값으로 내리는 판단"을 못 쓰는 행은 지웁니다.** 지우는 게 아깝다면 "나중에 추가 후보" 목록으로 따로 빼두되, 1차 범위에는 넣지 않습니다.

주기 칸을 채울 때는 아래를 역산합니다.

- 잡으려는 현상의 지속 시간 → 그보다 최소 5–10배 촘촘하게
- 진동처럼 주파수 분석이 필요하면 → 관심 주파수의 2배 이상(나이퀴스트), 실무에선 2.5–5배
- 환경값처럼 느린 변화 → 분 단위로 충분. 촘촘하게 받아봐야 저장 비용만 늘어남

같은 표를 그대로 두고 **하루치 데이터 양**을 미리 계산해보면 3계층 설계가 현실적으로 바뀝니다.

```python
# 하루 저장량 거친 추정 — 범위 정의서에 숫자 하나 박아두는 용도
tags = [
    # (태그 수, 주기(초), 행당 바이트)
    (3, 1.0,   50),   # 온도 3대
    (3, 0.1,   50),   # 진동 3대
    (3, 1.0,   50),   # 전류 3대
    (1, 300.0, 50),   # 구역 환경
]

per_day = sum(n * (86400 / period) * size for n, period, size in tags)
print(f"원본 기준 약 {per_day / 1024**2:.1f} MB/일, {per_day * 365 / 1024**3:.1f} GB/년")
# → 원본 기준 약 148.3 MB/일, 52.9 GB/년
```

설비 3대에 태그 10개뿐인데도 연 50GB가 나옵니다. 이 숫자를 미리 보면 "원본을 영원히 보관한다"는 선택지가 왜 성립하지 않는지, Day 10의 다운샘플링 정책이 왜 설계 단계의 결정인지가 명확해집니다.

### 모델 범위 — 셋 중 무엇을 1차에 넣을지

Day 04의 4계층은 자산·형상·거동 세 조각으로 나뉩니다. 1차 릴리스에서 셋을 모두 완성하려 하지 말고, 각각 **어느 수준까지**인지 적습니다.

| 모델 | 1차 릴리스 수준 | 2차 이후 |
|---|---|---|
| 자산 모델 | 공장-라인-설비-센서 4단 계층, 식별자 규칙 확정 | 설비 간 공정 흐름 관계 추가 |
| 형상 모델 | 설비 3대 + 바닥/벽 저폴리곤, 노드-자산 ID 매핑 완료 | 주변 설비·배관, 스캔 기반 정밀화 |
| 거동 모델 | 없음 (임계값 규칙만) | 상태 머신, 이상 탐지 모델 |

자산 모델만 "확정"이라고 쓰고 나머지는 "현 수준"이라고 쓴 이유는 Day 04의 팁 그대로입니다. 3D는 나중에 교체할 수 있지만, 식별자 체계를 뒤늦게 바꾸면 그동안 쌓인 데이터가 전부 고아가 됩니다.

## 5. 항목 6–7: 성공 기준과 제약

### 성공 기준은 트윈의 성능이 아니라 현실의 변화로

"60 FPS로 동작한다", "지연 1초 이내" 같은 건 시스템 지표이지 성공 기준이 아닙니다. 두 종류를 나눠서 씁니다.

**결과 지표 (이게 진짜 성공 기준)**
- 과열로 인한 계획 외 정지: 월 평균 2.1회 → 1회 이하
- 이상 인지까지 걸리는 시간: 평균 50분(순회 주기) → 15분 이내
- 야간 현장 순회: 4회/야간 → 2회/야간

**시스템 지표 (결과 지표를 떠받치는 조건)**
- 센서 → 화면 종단 지연: 95퍼센타일 3초 이내
- 데이터 결측률: 태그당 월 1% 이하
- 경보 오탐: 주 3건 이하 (이걸 넘으면 사람이 경보를 무시하기 시작)

마지막 항목이 실무에서 가장 과소평가됩니다. **오탐이 잦은 경보는 없는 경보보다 나쁩니다.** 사람이 무시하는 법을 배우고, 그 습관은 진짜 경보에도 적용되기 때문입니다.

결과 지표를 쓰려면 **현재 값(베이스라인)** 이 필요합니다. 베이스라인이 없다면, 트윈을 만들기 전에 몇 주간 수기로라도 세어두는 게 Phase 2보다 먼저 할 일입니다. 비교 대상이 없으면 완성 후에 성공 여부를 증명할 방법이 없습니다.

### 제약과 가정은 "틀렸을 때 무슨 일이 생기는지"까지

7번 항목은 목록만 나열하면 쓸모가 없습니다. 각 줄에 **깨졌을 때의 영향**을 붙입니다.

```
가정: 현장 네트워크는 하루 최대 10분 단절된다.
  → 깨지면: 엣지 버퍼 용량 재산정 필요 (Day 11)

제약: OT망에서 IT망으로의 아웃바운드만 허용. 인바운드 불가.
  → 영향: 폴링 방식 불가, 엣지에서 밀어 올리는 구조 강제 (Day 37)

가정: P-02는 구형 설비라 PLC 통신 포트가 없다.
  → 깨지면: 외장 센서 부착 필요, 설치 일정 +2주

제약: 1차 릴리스 기한 8주, 개발 인력 1명.
  → 영향: 거동 모델은 1차 범위 밖으로 확정
```

두 번째 줄의 OT/IT 방향 제약은 산업 현장에서 거의 항상 등장하고, 거의 항상 아키텍처를 바꿉니다. 이걸 8주차에 발견하면 2–3계층을 다시 만들어야 합니다. 문서 작성 시점에 보안 담당자에게 **"어느 방향 연결이 허용되나요"** 한 문장만 물어보면 되는 일입니다.

## 6. 1주차 회고 — Phase 1에서 고정된 것들

Day 01–05를 통과하면서 앞으로 바뀌지 않을 기준선이 몇 개 생겼습니다.

1. **디지털 트윈 = 3D + 실시간 데이터가 아니다** (Day 01). 현실과의 연결, 모델, 그리고 그 모델이 만드는 판단이 있어야 트윈입니다. 3D는 선택 사항이고, 때로는 없는 편이 낫습니다.
2. **성숙도는 단계적으로 오른다** (Day 02). 아래 단계의 데이터 품질이 위 단계의 천장입니다.
3. **산업마다 어려운 지점이 다르다** (Day 03). 제조는 설비 이질성, 건설은 BIM 정보 손실, 물류는 규모, 에너지는 물리 모델의 정확도.
4. **5계층 중 4계층(모델)이 트윈을 트윈으로 만든다** (Day 04). 1–3계층만 있으면 그냥 IoT 대시보드입니다.
5. **되돌리기 어려운 결정은 코드보다 먼저 쓴다** (Day 05). 식별자 체계, 타임스탬프 정책, 보존 정책, 범위 밖 선언.

다음 Phase 2(Day 06–11)부터는 1–3계층을 직접 만듭니다. 센서를 고르고, 프로토콜을 붙이고, 브로커와 시계열 DB를 띄웁니다. 그 작업을 하는 내내 오늘 쓴 데이터 인벤토리 표가 체크리스트 역할을 합니다 — 표에 없는 태그를 수집하고 있다면 범위가 번지고 있다는 뜻이고, 표에 있는데 아직 못 받고 있다면 그게 남은 일입니다.

> 💡 **실무 팁**: 범위 정의서를 Git 저장소의 `docs/scope.md`로 두고 코드와 같이 버전 관리하세요. PR로 범위를 바꾸게 만들면, 범위 변경이 암묵적으로 일어나지 않고 기록으로 남습니다.

## 📝 핵심 요약

1. 범위 정의서는 A4 두 장짜리 문서로, 나중에 되돌리기 어려운 결정(식별자 체계·타임스탬프·보존 정책·경계)만 미리 못 박는 것이 목적이다.
2. 목적은 "모니터링한다"가 아니라 "누가 어떤 판단을 어떻게 다르게 내리는가"로 쓴다. 이 문장이 나머지 항목의 수치를 결정한다.
3. 범위는 Out of scope를 같은 분량으로 써야 생긴다. 1차 릴리스에서 설비 제어(쓰기)를 범위 밖으로 선언하는 것이 거의 항상 옳다.
4. 데이터 인벤토리는 태그·주기·프로토콜·보존·판단을 담은 표로 쓰고, 하루 저장량을 미리 계산해 3계층 설계를 현실화한다.
5. 성공 기준은 시스템 지표가 아니라 결과 지표로 쓰되, 비교할 베이스라인을 트윈 제작 전에 확보해 둔다.
