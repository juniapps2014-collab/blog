## 1. 왜 계층으로 쪼개야 하는가

Day 03까지는 "디지털 트윈이 무엇이고 어디에 쓰이는가"를 봤습니다. 이제 **어떻게 생겼는가**로 넘어갑니다.

디지털 트윈 프로젝트가 실패하는 전형적인 방식은 이렇습니다. 센서를 붙이고, 데이터를 받아서, Unity 화면에 숫자를 띄웁니다. 데모는 멋지게 돌아갑니다. 그런데 센서를 10개에서 200개로 늘리는 순간, 혹은 "작년 3월 데이터로 되감아 보자"는 요구가 들어오는 순간 전부 다시 만들어야 합니다. 수집·저장·시각화가 하나의 덩어리로 얽혀 있기 때문입니다.

계층을 나누는 목적은 **한 계층을 교체해도 나머지가 버티게 만드는 것**입니다. MQTT 브로커를 Mosquitto에서 클라우드 IoT 허브로 바꿔도 Unity 쪽은 그대로여야 하고, 화면을 Unity에서 웹 대시보드로 바꿔도 수집 파이프라인은 손대지 않아야 합니다.

상용 플랫폼들이 제시하는 구조도 이름만 다를 뿐 결국 같은 다섯 덩어리로 수렴합니다. 이 시리즈에서는 아래 5계층을 기준으로 삼고, 앞으로의 모든 회차를 이 지도 위에 올려놓겠습니다.

| 계층 | 한 줄 정의 | 다루는 회차 |
|---|---|---|
| 1. 물리 (Physical) | 실제 설비·공간과 거기 붙은 센서/액추에이터 | Day 06 |
| 2. 수집 (Acquisition) | 신호를 디지털 값으로 바꿔 밖으로 내보내는 구간 | Day 07–09, 11 |
| 3. 연결 (Connectivity) | 전송·버퍼링·저장. 데이터의 혈관과 창고 | Day 10–11 |
| 4. 모델 (Model) | 자산 구조·메타데이터·3D 형상·시뮬레이션 로직 | Day 12–17, 24–28 |
| 5. 서비스 (Service) | 사람이나 다른 시스템이 소비하는 출구 | Day 18–23, 29–33 |

## 2. 1계층 — 물리: 트윈의 정확도 상한선

가장 자주 과소평가되는 계층입니다. **물리 계층의 품질이 트윈 전체의 정확도 상한선을 결정합니다.** 위에서 아무리 정교한 모델을 돌려도, 10초마다 한 번 읽는 온도 센서로는 1초 단위 과열 이벤트를 절대 잡을 수 없습니다.

이 계층에서 결정해야 하는 것은 세 가지입니다.

**무엇을 측정할 것인가** — 알고 싶은 현상을 직접 측정할 수 없을 때가 많습니다. "베어링 마모도"를 재는 센서는 없습니다. 대신 진동과 전류를 재고, 그 신호에서 마모 징후를 추론합니다. 이렇게 **직접 측정 불가능한 양을 측정 가능한 신호로 번역하는 작업**이 물리 계층 설계의 핵심입니다.

**얼마나 자주 측정할 것인가** — 샘플링 주기는 잡고 싶은 현상의 시간 척도에서 역산합니다. 진동 분석처럼 수 kHz가 필요한 경우와, 건물 실내 온도처럼 5분이면 충분한 경우는 이후 모든 계층의 설계를 바꿉니다.

**측정하지 않을 것은 무엇인가** — 센서를 많이 달수록 좋다는 생각은 비용과 운영 부담으로 되돌아옵니다. 쓰이지 않는 태그는 저장 비용과 장애 지점만 늘립니다.

> 💡 **실무 팁**: 센서 목록을 만들 때 각 항목 옆에 "이 값이 바뀌면 누가 무슨 결정을 하는가"를 한 줄로 적어보세요. 답을 못 쓰는 센서는 대개 필요 없는 센서입니다.

## 3. 2계층 — 수집: 프로토콜의 전쟁터

물리 신호를 디지털 값으로 바꾸고, 그 값을 외부에서 읽을 수 있게 내놓는 구간입니다. 현장에서 가장 많은 시간을 잡아먹는 계층이기도 합니다. 설비마다 말이 다르기 때문입니다.

실무에서 만나는 조합은 대략 이렇습니다.

| 출처 | 전형적 인터페이스 | 성격 |
|---|---|---|
| 구형 PLC·계측기 | Modbus TCP/RTU | 단순, 주소 기반, 의미 정보 없음 |
| 현대 산업 설비 | OPC UA | 주소 공간에 타입·의미 포함 |
| IoT 센서·게이트웨이 | MQTT | 경량 발행/구독, 네트워크에 관대 |
| 상위 시스템 | REST / DB 직접 조회 | 주기 느림, 배치 성격 |

Modbus와 OPC UA의 차이를 한 가지만 짚으면, **의미(semantics)의 유무**입니다. Modbus는 "레지스터 40001의 값이 752"라고만 알려줍니다. 그게 섭씨 75.2도인지 회전수인지는 사람이 별도 문서를 보고 알아야 합니다. OPC UA는 노드에 타입·단위·엔지니어링 범위가 붙어 있어 클라이언트가 서버를 탐색(browse)하는 것만으로 의미를 알 수 있습니다. 이 차이가 4계층(모델)의 작업량을 크게 좌우합니다.

수집 계층에서 반드시 정해야 할 한 가지는 **타임스탬프의 주인**입니다.

- 센서/PLC가 찍은 시각(source timestamp)
- 게이트웨이가 받은 시각
- 서버가 저장한 시각

셋은 항상 다릅니다. 네트워크가 끊겼다 복구되면 수 분씩 벌어지기도 합니다. 트윈이 "언제의 상태인가"를 말하려면 **source timestamp를 끝까지 들고 가야 합니다.** 이 원칙을 초반에 정하지 않으면, 나중에 리플레이(Day 28)를 구현할 때 데이터가 시간순으로 엉켜 있는 걸 발견하게 됩니다.

## 4. 3계층 — 연결: 흐름과 저장을 분리하라

수집된 값을 실어 나르고 쌓아두는 계층입니다. 여기서 가장 중요한 설계 판단은 **실시간 흐름과 이력 저장을 서로 다른 경로로 다루는 것**입니다.

```
                    ┌──► [실시간 구독] ──► 서비스 계층 (화면, 경보)
센서 ─► 게이트웨이 ─┤
                    └──► [시계열 DB] ───► 분석, 리플레이, 학습
```

하나의 경로로 합치면 문제가 생깁니다. DB에 쓰고 나서 읽어서 화면에 올리면 지연이 쌓이고, 반대로 화면으로만 보내면 이력이 남지 않아 Phase 6의 학습 데이터가 없습니다. 발행/구독 브로커가 들어오는 값을 두 방향으로 동시에 흘려보내는 구조가 표준에 가깝습니다.

이 계층에서 미리 못 박아야 할 것들:

**토픽/태그 명명 규칙** — `factory/line1/press01/temperature` 처럼 계층적이고 일관된 이름을 처음부터 강제합니다. 센서 5개일 때는 아무래도 상관없지만 200개가 되면 이름이 곧 시스템의 구조가 됩니다. Day 16에서 설비 태그와 3D 노드를 매핑할 때 이 규칙이 그대로 연결 고리가 됩니다.

**보존 정책(retention)** — 1초 단위 원본을 영원히 보관할 수는 없습니다. "원본 7일 → 1분 평균 90일 → 1시간 평균 2년" 같은 단계적 다운샘플링을 처음부터 설계합니다. 저장 비용 문제이기도 하지만, **더 중요하게는 질의 성능 문제**입니다(Day 10).

**연결 끊김 대응** — 현장 네트워크는 끊깁니다. 엣지에서 로컬 버퍼에 쌓았다가 복구 시 밀어 넣는 store-and-forward가 기본 전제입니다(Day 11). 이때 밀려 들어온 과거 데이터를 "지금 값"으로 오해하지 않으려면 다시 source timestamp가 필요합니다.

## 5. 5계층을 먼저 보기 전에 — 4계층이 트윈을 트윈으로 만든다

여기서 잠깐 정리하면, 1–3계층은 사실 **IoT 시스템이면 다 갖고 있는 구조**입니다. 센서 달고, 모아서, 저장하고, 그래프 그리는 것까지는 디지털 트윈이라는 말을 쓰지 않아도 수십 년간 해오던 일입니다.

디지털 트윈을 디지털 트윈으로 만드는 건 **4계층(모델)** 입니다. Day 01에서 "3D 모델과 디지털 트윈은 다르다"고 했던 그 구분선이 정확히 여기 있습니다. 모델 계층은 세 가지로 구성됩니다.

**① 자산 모델 (구조)** — 공장 안에 라인이 있고, 라인 안에 설비가 있고, 설비에 센서가 붙어 있다는 **관계 그래프**입니다. 숫자 한 줄이 "어느 설비의 어떤 속성인지" 알 수 있게 해줍니다. Azure Digital Twins의 DTDL이나 독일 Industrie 4.0 진영의 AAS(Asset Administration Shell)가 이 영역의 표준화 시도입니다(Day 17).

```json
// DTDL 스타일 모델 조각 — 설비 타입 정의 (개념 예시)
{
  "@id": "dtmi:factory:Press;1",
  "@type": "Interface",
  "contents": [
    { "@type": "Property",  "name": "serialNumber", "schema": "string" },
    { "@type": "Telemetry", "name": "temperature",  "schema": "double" },
    { "@type": "Relationship", "name": "installedIn", "target": "dtmi:factory:Line;1" }
  ]
}
```

여기서 핵심은 `Telemetry`(계속 흘러드는 값)와 `Property`(비교적 고정된 속성), 그리고 `Relationship`(구조)을 **명시적으로 구분한다**는 점입니다. 이 구분이 있어야 "3번 라인에 속한 모든 프레스의 현재 온도"같은 질의가 성립합니다.

**② 형상 모델 (3D)** — 실제 공간의 기하학적 표현입니다. CAD/BIM/스캔에서 가져오며(Day 12–14), 좌표계와 원점을 현실과 맞추고(Day 15), 각 3D 노드가 어느 자산에 대응하는지 연결합니다(Day 16). **3D 노드와 자산 ID의 매핑 테이블이 없으면 그냥 예쁜 모델일 뿐입니다.**

**③ 거동 모델 (시뮬레이션)** — 물리 법칙이나 학습된 관계로 "이 상태에서 이렇게 하면 어떻게 될까"를 계산하는 부분입니다. 상태 머신, 이산사건 시뮬레이션, 예측 모델이 여기 들어갑니다(Phase 5–6). Day 02의 성숙도 3단계(예측) 이상으로 올라가려면 반드시 필요한 조각입니다.

> 💡 **실무 팁**: 셋 중 하나만 먼저 만들어야 한다면 **자산 모델**입니다. 3D는 나중에 붙일 수 있고 시뮬레이션은 나중에 배울 수 있지만, 자산 구조를 뒤늦게 바꾸면 그동안 쌓인 데이터의 식별자가 전부 틀어집니다.

## 6. 5계층 — 서비스: 출구는 화면만이 아니다

모델 계층이 만든 결과를 소비자에게 내보내는 계층입니다. 대부분의 사람이 디지털 트윈 하면 떠올리는 3D 화면이 여기 있지만, 출구는 그것만이 아닙니다.

| 소비자 | 출구 형태 | 관련 회차 |
|---|---|---|
| 현장 운영자 | 3D 뷰어, 대시보드, 경보 | Day 18–23 |
| 분석가 | 리포트, What-if 시나리오 비교 | Day 27 |
| 다른 시스템 | REST/GraphQL API, 이벤트 발행 | Day 34–35 |
| 누구든 | 자연어 질의(LLM) | Day 33 |

주의할 점은 **서비스 계층에 로직을 넣지 않는 것**입니다. "온도가 80도를 넘으면 경고"라는 판단을 Unity 스크립트 안에 넣으면, 웹 대시보드를 추가하는 순간 같은 규칙을 두 번 구현하게 되고 둘은 반드시 어긋납니다. 판단은 모델 계층에서, 화면은 그 결과를 **표시만** 합니다.

그리고 Day 02에서 말한 성숙도 5단계(자율)로 가려면 이 계층에 **역방향 경로**가 생깁니다. 트윈의 결정이 1계층의 액추에이터로 되돌아가 실제 설비를 움직이는 겁니다. 이 순간 시스템의 성격이 완전히 달라집니다 — 읽기 전용 시스템이 쓰기 가능 시스템이 되고, 보안과 안전 요구사항이 몇 배로 뛰어오릅니다(Day 37).

## 7. 내 프로젝트를 5계층 위에 올려보기

이 시리즈의 캡스톤(Day 40)인 미니 스마트팩토리 트윈을 5계층에 배치하면 이렇게 됩니다.

| 계층 | 캡스톤에서의 구현 |
|---|---|
| 물리 | 온도·진동 센서(또는 시뮬레이터)가 붙은 가상 설비 2–3대 |
| 수집 | 센서 → MQTT 발행 (Day 08) |
| 연결 | Mosquitto 브로커 + InfluxDB 저장, 토픽 규칙 고정 (Day 10) |
| 모델 | 설비 계층 구조 + glTF 3D 모델 + 이상 탐지 규칙 (Day 16, 29) |
| 서비스 | Unity 실시간 뷰 + 경보 타임라인 + 리플레이 (Day 21, 23, 28) |

Day 05에서 쓸 "범위 정의서"는 결국 이 표를 **내 프로젝트 버전으로 채우는 작업**입니다. 지금 단계에서 유용한 자가 진단은 이렇습니다.

1. 다섯 칸 중 **비어 있는 칸**이 있는가? (대개 모델 계층이 비어 있고, 그 프로젝트는 트윈이 아니라 대시보드입니다)
2. 각 계층 사이의 **인터페이스를 한 문장으로** 쓸 수 있는가? (쓸 수 없다면 그 경계는 아직 뒤섞여 있습니다)
3. 어느 한 칸의 구현을 통째로 바꿨을 때, **다른 칸을 몇 개나 고쳐야 하는가?** (2개 이상이면 결합이 과합니다)

## 📝 핵심 요약

1. 디지털 트윈은 물리·수집·연결·모델·서비스 5계층으로 나뉘며, 계층을 나누는 목적은 한 계층을 교체해도 나머지가 버티게 하는 것이다.
2. 물리 계층의 측정 대상과 샘플링 주기가 트윈 전체의 정확도 상한선을 결정한다. 직접 잴 수 없는 현상을 잴 수 있는 신호로 번역하는 게 설계의 핵심이다.
3. 수집 계층에서는 프로토콜 선택(Modbus/OPC UA/MQTT)과 함께 source timestamp를 끝까지 보존할 것을 먼저 못 박아야 한다.
4. 연결 계층은 실시간 흐름과 이력 저장을 분리하고, 명명 규칙·보존 정책·연결 끊김 대응을 초기에 고정한다.
5. 1–3계층은 일반 IoT와 다르지 않다. 자산 모델·형상 모델·거동 모델로 구성된 4계층(모델)이 IoT 시스템을 디지털 트윈으로 만든다.
