## 1. 세 가지 불일치 — 증상으로 구분하기

Day 13에서 변환한 glTF와 Day 14에서 정리한 스캔 메시를 한 씬에 올리면, 거의 항상 뭔가 어긋납니다. 중요한 건 **어긋남의 종류가 셋뿐이고, 증상만 보면 바로 구분된다**는 점입니다.

| 증상 | 원인 | 전형적인 배수/각도 |
|---|---|---|
| 모델이 먼지처럼 작거나 산처럼 큼 | **단위 불일치** | 1000배, 0.001배, 0.0254배 |
| 모델이 누워 있거나 뒤집힘 | **축 방향(up-axis) 불일치** | X축 ±90° |
| 모델이 거울상 — 글자가 뒤집혀 보임 | **손 방향(handedness) 불일치** | 한 축 부호 반전 |
| 모델이 화면 밖 어딘가에 있음 | **원점 불일치** | 수십만~수백만 단위 이동 |
| 가까이 가면 지오메트리가 떨림 | **원점이 너무 멀다** | float 정밀도 한계 |

한 번에 다 고치려 하지 말고 **단위 → 축 → 원점 순서로** 잡으세요. 단위가 1000배 틀린 상태에서 원점 오프셋을 재면 그 값이 다시 1000배 틀립니다. 축이 누운 상태에서 원점을 맞추면 축을 세우는 순간 원점이 또 틀어집니다. 이 순서는 변환 합성 순서(Scale → Rotate → Translate)와 같아서, 거꾸로 하면 반드시 다시 해야 합니다.

## 2. 단위 — 숫자는 같은데 뜻이 다르다

### 포맷별 규약

| 출처 | 기본 단위 | 단위 정보가 파일에 들어있나 |
|---|---|---|
| STEP (AP203/214/242) | 파일에 명시 (대개 mm) | **있음** — `SI_UNIT(.MILLI.,.METRE.)` |
| IFC | 프로젝트별 (대개 mm 또는 m) | **있음** — `IfcUnitAssignment` |
| glTF 2.0 | **미터 고정** | 불필요 (스펙이 고정) |
| FBX | 파일 헤더의 `UnitScaleFactor` | 있지만 툴마다 해석이 다름 |
| OBJ | **없음** | **없음** — 숫자뿐 |
| Unity | 미터 | — |
| 포인트 클라우드(E57/LAS) | 대개 미터 | E57은 있음, PLY/XYZ는 없음 |

실무에서 사고가 나는 지점은 분명합니다. **STEP과 IFC는 단위가 파일에 들어 있어서 변환기가 알아서 처리해 주지만, OBJ와 일부 FBX는 그렇지 않습니다.** 협력업체에서 받은 OBJ 한 덩어리는 그 숫자가 mm인지 m인지 inch인지 파일만 봐서는 알 수 없습니다.

```
탱크 지름 실측 2,400mm

  mm로 저장된 OBJ → Unity에서 2400 유닛 = 2.4km 지름
  m로 저장된 OBJ  → Unity에서 2.4 유닛  = 2.4m 지름  ✓
  inch로 저장      → Unity에서 94.5 유닛 = 94.5m 지름
```

### 판별법

단위를 모르는 파일을 받으면, **크기를 아는 것 하나를 골라 바운딩 박스를 재는 게** 가장 빠릅니다.

```python
# trimesh로 바운딩 박스 크기만 확인
import trimesh

m = trimesh.load("unknown.obj")
print(m.bounds)          # [[minx,miny,minz],[maxx,maxy,maxz]]
print(m.extents)         # 각 축 길이

# 실측 2.4m 탱크인데 extents가 [2400, 3100, 2400]이면 → mm
# [2.4, 3.1, 2.4]면 → m
# [94.5, 122, 94.5]면 → inch
```

기준으로 삼기 좋은 건 **사람 눈높이에 있는 규격품**입니다. 문 높이(2,100mm), 계단 챌판(180mm), 파이프 플랜지, 유럽 파렛트(1,200×800mm), 콘크리트 기둥 간격. 설비 자체의 치수보다 이쪽이 확실합니다.

> 💡 **실무 팁**: 임포트 시 스케일로 맞추는 것(Unity Import Settings의 Scale Factor)과 Transform의 `localScale`로 맞추는 것은 **전혀 다릅니다.** 전자는 메시 데이터 자체를 바꿔 피직스·라이트맵·NavMesh에 올바로 반영되지만, 후자는 렌더링만 바꿔 놓고 콜라이더·파티클·물리 계산에서 계속 사고를 냅니다. **반드시 임포트 단계에서 잡으세요.** `localScale`이 1이 아닌 오브젝트가 씬에 남아 있다면, 그건 나중에 터질 부채입니다.

## 3. 축 방향과 손 방향 — 누웠는가, 뒤집혔는가

### Up-axis

| 환경 | Up축 | 손 방향 |
|---|---|---|
| Unity | **Y** | **왼손** |
| glTF 2.0 | **Y** | 오른손 |
| Blender | **Z** | 오른손 |
| USD / Omniverse | 기본 **Y** (`upAxis` 메타데이터로 Z 지정 가능) | 오른손 |
| CAD (STEP) / IFC | **Z** | 오른손 |
| 측량·GIS | **Z** (높이) | 오른손 |
| Unreal | **Z** | 왼손 |

규칙성이 보입니다. **엔지니어링·측량 계열은 전부 Z-up, 리얼타임 그래픽스 계열은 Y-up**입니다. 지도는 평면이 XY고 높이가 Z인 게 자연스럽고, 화면은 위아래가 Y인 게 자연스러우니 당연한 분화입니다. 디지털 트윈은 이 두 세계를 잇는 일이라서 이 변환을 피할 수 없습니다.

Z-up 오른손 → Y-up 오른손 변환은 X축 기준 -90° 회전입니다.

```
Z-up (x, y, z)  →  Y-up (x, z, -y)

  CAD에서 (10, 5, 3)  — 동쪽 10m, 북쪽 5m, 높이 3m
  → glTF에서 (10, 3, -5)
```

### Handedness

손 방향이 다르면 회전 방향이 반대가 되고, 모델이 **거울상**이 됩니다. glTF(오른손) → Unity(왼손)는 한 축의 부호를 뒤집어 처리하는데, Unity의 glTF 임포터는 관례적으로 **Z축**을 뒤집습니다.

```
glTF 오른손 Y-up (x, y, z)  →  Unity 왼손 Y-up (x, y, -z)
```

그래서 CAD(Z-up 오른손)에서 Unity까지의 전체 변환은 이렇게 합성됩니다.

```
CAD Z-up 오른손 (x, y, z)
   │ ① Z-up → Y-up        (x, z, -y)
   │ ② 오른손 → 왼손       Z 부호 반전
   ↓
Unity Y-up 왼손   (x, z, y)
```

즉 **CAD의 Y와 Z를 맞바꾸면 끝**입니다. 중간 단계를 따로 외울 필요 없이 이 한 줄만 기억하면 됩니다.

### 거울상인지 어떻게 아는가

육안으로는 대칭형 설비에서 구분이 안 됩니다. 확인 방법 둘.

- **비대칭 표식을 넣습니다.** 모델에 글자(명판, 'FRONT' 텍스트)나 비대칭 돌출부가 있으면 즉시 보입니다. 없으면 원점에 L자 마커를 임시로 하나 붙이세요
- **행렬식 부호를 봅니다.** 변환 행렬의 상위 3×3 행렬식이 음수면 반전(improper rotation)이 섞인 겁니다

```python
import numpy as np

R = M[:3, :3]
if np.linalg.det(R) < 0:
    print("거울상 — handedness 변환이 중복 적용됐을 가능성")
```

> 💡 **실무 팁**: 거울상 사고의 절반은 **변환을 두 번 적용해서** 생깁니다. 변환기(Blender 익스포터, cgltf, Assimp)가 이미 축을 바꿔 줬는데, 임포트 쪽에서도 "Convert Axis" 옵션이 켜져 있는 식입니다. 새 파이프라인을 세울 때는 **중간 단계마다 축 변환 옵션을 전부 끄고 한 번 통과시켜 보세요.** 어디서 바뀌는지 확인한 뒤 한 곳에서만 켜는 게 두 곳을 추측으로 조합하는 것보다 훨씬 빠릅니다.

## 4. 원점 — 지도 좌표를 그대로 쓰면 떨린다

### float 정밀도라는 벽

측량 성과표에는 설비 위치가 EPSG:5186(중부원점 TM, 한국) 기준으로 이렇게 찍혀 있습니다.

```
P-101  X = 198,432.187   Y = 551,209.643   H = 32.415
```

이걸 그대로 Unity에 넣으면 작동은 합니다. 그런데 카메라를 설비 가까이 가져가는 순간 **지오메트리가 미세하게 떨리고, 그림자가 깜빡이고, 콜라이더가 어긋납니다.**

이유는 단정적입니다. Unity의 Transform은 32비트 float이고, float의 유효 자릿수는 약 7자리입니다.

| 원점으로부터 거리 | float 해상도 |
|---|---|
| 1 m | 약 0.00000012 m |
| 1,000 m | 약 0.00012 m |
| 100,000 m | 약 0.0078 m |
| **551,209 m** | **약 0.031 m** |
| 1,000,000 m | 약 0.0625 m |

좌표값이 55만이면 표현 가능한 최소 간격이 **3cm**입니다. 밀리미터 정밀도로 스캔한 배관을 3cm 격자 위에 올려 놓는 셈이고, 카메라가 움직이며 뷰 행렬 계산이 반복되면 그 오차가 프레임마다 흔들려 떨림으로 보입니다.

### 해결 — 로컬 원점을 정한다

방법은 단순합니다. **사이트 안의 한 점을 Unity 원점(0,0,0)으로 정하고, 모든 좌표를 그 점으로부터의 상대값으로 바꿉니다.**

```
Unity 좌표 = (측량 좌표 − 사이트 원점)을 축 변환한 값

  사이트 원점: X0 = 198,400,  Y0 = 551,200,  H0 = 30.0
  P-101:  (198432.187 − 198400, 551209.643 − 551200, 32.415 − 30.0)
        = (32.187, 9.643, 2.415)   ← Z-up
        → Unity (32.187, 2.415, 9.643)   ← Y·Z 교환
```

이제 좌표값이 세 자리이므로 float 해상도가 마이크로미터 수준입니다. 떨림은 사라집니다.

사이트 원점은 이렇게 고릅니다.

- **사이트 바깥이 아니라 안쪽**, 가급적 중심 근처. 반경이 작을수록 정밀도가 좋습니다
- **딱 떨어지는 값**으로 (198,400 / 551,200처럼). 손으로 역산할 일이 반드시 생깁니다
- **건물 모서리나 측량 기준점처럼 현장에서 다시 찾을 수 있는 지물 근처**로. 나중에 추가 스캔을 정합할 때 필요합니다
- **한 번 정하면 절대 바꾸지 않습니다.** 프로젝트 상수로 박고 문서화하세요

> 💡 **실무 팁**: 사이트 원점은 **코드 한 곳에 상수로 두고, 변환 함수를 거쳐서만 좌표를 다루세요.** `transform.position`에 측량 좌표를 직접 대입하는 코드가 한 줄이라도 생기면 그때부터 두 좌표계가 뒤섞입니다. 특히 Day 19에서 MQTT로 들어오는 센서 페이로드에 위경도나 측량 좌표가 실려 오는 경우가 많으니, **수신 지점에서 한 번에 변환**해 넘기는 구조를 처음부터 잡아 두는 게 좋습니다.

```csharp
// 사이트 좌표 변환은 한 곳에서만
public static class SiteOrigin
{
    // EPSG:5186 기준. 프로젝트 수명 동안 변경 금지.
    const double E0 = 198400.0;   // Easting
    const double N0 = 551200.0;   // Northing
    const double H0 = 30.0;       // 표고 (m)

    /// 측량 좌표(Z-up, m) → Unity 로컬 좌표(Y-up, 왼손)
    public static Vector3 ToUnity(double e, double n, double h)
    {
        return new Vector3(
            (float)(e - E0),   // X: 동쪽
            (float)(h - H0),   // Y: 높이
            (float)(n - N0));  // Z: 북쪽
    }

    public static (double e, double n, double h) ToSurvey(Vector3 p)
        => (p.x + E0, p.z + N0, p.y + H0);
}
```

double로 받아 뺄셈을 **먼저** 하고 그 결과만 float으로 캐스팅하는 게 핵심입니다. `(float)e - (float)E0`로 쓰면 뺄셈 전에 이미 정밀도를 잃어 의미가 없습니다.

### 사이트가 여러 개이거나 너무 넓다면

반경 수 km를 넘어가면(공항, 항만, 도시 규모) 원점 하나로는 부족합니다. 선택지는 둘입니다.

- **구역별 원점 + 스트리밍**: 구역마다 원점을 두고 카메라가 들어간 구역만 로드. Day 38의 WebGL 배포에서도 유리합니다
- **Floating origin**: 카메라가 일정 거리 이상 멀어지면 씬 전체를 되돌려 카메라를 다시 원점 근처로 가져오는 방식. 코드가 복잡해지고 물리·파티클과 충돌할 수 있어, 가능하면 첫 번째를 권합니다

## 5. 정렬 — 기준점 3개와 강체 변환

단위·축·원점을 다 맞춰도 **스캔 데이터와 CAD 모델이 서로 몇 도씩 틀어져 있는** 상황이 남습니다. 스캔은 스캐너가 서 있던 임의의 좌표계에, CAD는 설계 좌표계에 있기 때문입니다. 이걸 맞추는 게 정렬입니다.

### 대응점으로 변환 구하기

양쪽에서 **같은 물리적 지점 3개 이상**의 좌표를 알면, 둘을 잇는 강체 변환(회전 + 이동, 필요하면 균일 스케일)을 최소제곱으로 풀 수 있습니다. Kabsch / Umeyama 알고리즘입니다.

기준점으로 쓸 만한 것:

- **측량 타깃** (Day 14에서 바닥에 붙여 둔 것) — 가장 정확
- **건물 기둥의 바닥 중심** — 도면과 스캔 양쪽에서 찾기 쉬움
- **앵커 볼트 중심, 베이스 플레이트 모서리** — 설비 단위 정렬에 적합
- 바닥 면 자체 — 높이와 기울기만 잡을 때

점 3개는 최소값이고, 실무에서는 **5~8개를 서로 멀리 떨어뜨려** 잡습니다. 가까이 모인 점들로 맞추면 먼 쪽이 크게 틀어집니다.

```python
import numpy as np

def kabsch(src, dst, allow_scale=False):
    """src(N,3) → dst(N,3) 강체 변환. 반환: (R, t, s, rmse)"""
    src, dst = np.asarray(src, float), np.asarray(dst, float)
    cs, cd = src.mean(0), dst.mean(0)
    P, Q = src - cs, dst - cd

    U, S, Vt = np.linalg.svd(P.T @ Q)
    d = np.sign(np.linalg.det(Vt.T @ U.T))
    # 반사(거울상)를 배제 — 이 보정이 없으면 축이 뒤집힌 해가 나온다
    R = Vt.T @ np.diag([1.0, 1.0, d]) @ U.T

    s = (S * [1, 1, d]).sum() / (P ** 2).sum() if allow_scale else 1.0
    t = cd - s * R @ cs

    res = dst - (s * (R @ src.T).T + t)
    rmse = np.sqrt((res ** 2).sum(1).mean())
    return R, t, s, rmse


# 기준점: 왼쪽은 스캔 좌표, 오른쪽은 측량 성과표
scan = [[12.31, 4.08, 0.02], [45.90, 3.95, 0.01],
        [46.12, 38.44, 0.03], [11.88, 38.10, 0.00]]
survey = [[198412.3, 551204.1, 30.0], [198445.9, 551204.0, 30.0],
          [198446.1, 551238.5, 30.0], [198411.9, 551238.1, 30.0]]

R, t, s, rmse = kabsch(scan, survey, allow_scale=True)
print(f"scale={s:.6f}  rmse={rmse*1000:.1f} mm")
```

### 잔차를 반드시 읽는다

정렬에서 가장 중요한 건 변환 행렬이 아니라 **RMSE와 점별 잔차**입니다.

| RMSE | 해석 |
|---|---|
| ~5mm | 정상. 측량 타깃 기반 정렬의 기대값 |
| 10~30mm | 허용 가능. 기둥 중심 같은 추정 기준점이면 이 수준 |
| 50mm~ | **문제 있음.** 대응점 짝이 잘못됐거나 스케일이 안 맞음 |
| 한 점만 크게 튐 | 그 점의 대응을 잘못 지정했을 가능성. 빼고 다시 계산 |

`allow_scale=True`로 풀었을 때 나오는 **스케일 값도 진단 지표**입니다. 1.000에 가까워야 정상이고, 0.983 같은 값이 나오면 Day 14의 포토그래메트리 스케일 보정이 덜 된 상태입니다. 1000이나 0.001이 나오면 단위 문제가 남아 있는 겁니다 — 2절로 돌아가세요.

> 💡 **실무 팁**: 정렬 결과는 **숫자로 검증한 뒤 반드시 눈으로도 봅니다.** 스캔 포인트 클라우드를 반투명으로, CAD 모델을 와이어프레임으로 겹쳐 놓고 돌려 보세요. RMSE가 8mm인데 눈으로 보니 배관 하나가 통째로 어긋나 있다면, 그건 정렬이 아니라 **현장이 도면과 다른 것**입니다. Day 14에서 말한 "현실을 확인하는 수단"으로서의 스캔이 실제로 작동하는 순간이 여기입니다.

## 6. 운영 규칙 — 다시 틀어지지 않게

정렬은 한 번 하고 끝나는 작업이 아닙니다. 새 설비 모델이 추가되고, 추가 스캔이 들어오고, 협력업체가 FBX를 다시 보내옵니다. 그때마다 어긋나지 않으려면 **규칙이 문서가 아니라 자산과 코드에 박혀 있어야** 합니다.

### 프로젝트 좌표 규약 문서

Day 05의 범위 정의서 옆에 한 장을 더 둡니다. 내용은 이게 전부입니다.

```markdown
## 좌표 규약 (v1, 변경 금지)

- 측량 기준: EPSG:5186 (Korea 2000 / Central Belt 2010)
- 사이트 원점: E=198400.000, N=551200.000, H=30.000
  - 현장 위치: 1공장 북서측 기준점 BM-03에서 동쪽 12.3m
- Unity 축: Y-up, 왼손. X=동, Y=상, Z=북
- 단위: 미터 (모든 임포트 자산은 임포트 단계에서 미터로 정규화)
- 허용 오차: 설비 ±20mm, 건물 구조 ±50mm
- 변환 코드: Assets/Scripts/Site/SiteOrigin.cs 단일 진입점
```

### 임포트 자산 체크리스트

새 자산이 들어올 때마다 이 네 가지를 확인합니다.

1. **바운딩 박스 크기가 상식적인가** — 알고 있는 치수 하나와 대조
2. **Transform이 깨끗한가** — position·rotation 0, `localScale` 1. 아니면 임포트 설정으로 되돌리기
3. **원점이 의미 있는 곳에 있는가** — 설비는 바닥 중심, 회전하는 부품은 회전축 위(Day 20의 애니메이션 바인딩이 여기 의존합니다)
4. **거울상이 아닌가** — 명판 글자나 비대칭 돌출부로 확인

### 검증용 마커를 씬에 상주시키기

가장 효과적인 장치는 **검증 전용 오브젝트를 씬에 남겨 두는 것**입니다.

- 사이트 원점에 1m 축 기즈모 (X 빨강=동, Y 초록=상, Z 파랑=북)
- 측량 기준점 위치마다 작은 구 + 기준점 ID 라벨
- 10m 격자 바닥 평면

이 셋이 씬에 있으면, 새 자산을 올렸을 때 어긋남을 **드래그한 직후 눈으로** 발견합니다. 빌드에서는 비활성화하면 됩니다. 이 마커 없이 작업하다가 Day 19에서 실시간 데이터를 붙인 뒤에야 "센서 위치가 전부 북쪽으로 9m 밀려 있다"는 걸 발견하는 게 가장 비싼 경로입니다.

> 💡 **실무 팁**: 좌표 규약은 **Day 16의 명명 규칙과 한 세트로** 다루세요. 자산 이름이 `P-101`로 정리돼 있고 측량 성과표의 ID도 `P-101`이면, 정렬 검증을 스크립트로 자동화할 수 있습니다 — 씬의 오브젝트 위치와 성과표 좌표를 ID로 조인해 편차가 허용 오차를 넘는 것만 리스트로 뽑는 식입니다. 100개 설비를 눈으로 확인하는 것과는 비교가 안 됩니다.

## 📝 핵심 요약

1. 어긋남은 **단위·축 방향·원점** 세 종류뿐이고, 증상으로 바로 구분된다. 반드시 **단위 → 축 → 원점 순서로** 잡는다. 순서를 거꾸로 하면 앞 단계를 고칠 때마다 뒤 단계가 다시 틀어진다.
2. STEP·IFC·glTF는 단위 정보가 파일에 있지만 **OBJ와 일부 FBX는 없다.** 모르는 파일은 문 높이·파렛트 같은 규격품으로 바운딩 박스를 재서 판별하고, 보정은 반드시 **임포트 설정에서** 한다. `localScale`로 맞추면 물리·콜라이더에서 계속 사고가 난다.
3. 엔지니어링·측량은 Z-up 오른손, 리얼타임 그래픽스는 Y-up(Unity는 왼손)이다. **CAD → Unity는 Y와 Z를 맞바꾸면 끝**이고, 거울상은 변환이 두 번 적용돼 생기는 경우가 절반이다. 3×3 행렬식 부호로 확인한다.
4. 측량 좌표를 그대로 쓰면 float 유효 자릿수 7자리 한계로 **55만 m 지점에서 해상도가 3cm**가 되어 지오메트리가 떨린다. 사이트 안쪽의 딱 떨어지는 점을 원점으로 정하고, **double로 뺄셈한 뒤 float으로 캐스팅**하는 단일 변환 함수만 거쳐 좌표를 다룬다.
5. 스캔과 CAD의 정렬은 **멀리 떨어진 기준점 5~8개**로 Kabsch/Umeyama 강체 변환을 풀어 구한다. 변환 행렬보다 **RMSE와 점별 잔차, 그리고 추정된 스케일 값**이 중요하다. 스케일이 1.000에서 멀면 단위나 포토그래메트리 보정이 덜 된 것이다.
6. 좌표 규약은 문서 한 장(기준 좌표계·사이트 원점·축·단위·허용 오차·변환 코드 경로)으로 고정하고, **사이트 원점 기즈모와 기준점 마커를 씬에 상주시킨다.** 새 자산을 드래그한 직후 어긋남이 보이는 구조가, 실시간 데이터를 붙인 뒤 발견하는 것보다 훨씬 싸다.
