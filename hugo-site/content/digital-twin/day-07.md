## 1. 프로토콜은 "하나 고르는 것"이 아니다

Day 06에서 센서를 골랐으니 이제 그 값을 가져올 차례입니다. 그런데 "우리는 MQTT를 쓰기로 했다" 같은 문장은 실제 현장에서는 거의 의미가 없습니다. **한 공장의 데이터 경로에는 보통 세 가지가 전부 등장**하고, 각자 맡은 구간이 다르기 때문입니다.

전형적인 경로를 그려보면 이렇습니다.

```
[센서] ──4~20mA/디지털──> [PLC]
                             │
                   Modbus TCP │ (레지스터 폴링, 현장 네트워크)
                             ▼
                      [엣지 게이트웨이]
                             │
                  OPC UA      │ (설비 벤더 서버가 있는 경우 여기서 구독)
                             ▼
                      [엣지 게이트웨이]
                             │
                     MQTT     │ (방화벽을 나가 상위로, 아웃바운드 단일 연결)
                             ▼
                    [브로커 / 클라우드] ──> [시계열 DB] ──> [Unity 트윈]
```

구간마다 요구가 다릅니다. PLC 바로 앞은 **결정론적이고 단순**해야 하고, 설비 벤더 서버는 **구조화된 모델과 보안**을 제공하며, 공장 밖으로 나가는 구간은 **불안정한 네트워크를 견디고 방화벽을 통과**해야 합니다. 세 프로토콜은 각각 그 요구에 맞춰 설계된 물건입니다.

> 💡 **실무 팁**: 아키텍처 리뷰에서 "프로토콜 뭐 쓰나요"라는 질문이 나오면 구간을 되물으세요. 답이 하나로 나오는 상황은 신규 설비만 있는 그린필드뿐이고, 현실의 공장은 20년 된 설비와 작년에 들어온 설비가 같은 라인에 섞여 있습니다.

## 2. 세 프로토콜 한눈에 비교

| | Modbus (TCP/RTU) | OPC UA | MQTT |
|---|---|---|---|
| 등장 | 1979년 | 2008년(통합 아키텍처) | 1999년, 현재 OASIS 표준 |
| 통신 모델 | 마스터→슬레이브 폴링 | 클라이언트/서버 세션 + 구독, PubSub 확장 | 발행/구독 (브로커 경유) |
| 데이터 모델 | 없음 — 숫자 레지스터뿐 | 있음 — 타입·단위·계층을 서버가 노출 | 없음 — 토픽 문자열 + 바이트 페이로드 |
| 자체 설명성 | ❌ 외부 문서 필요 | ✅ 브라우징으로 발견 가능 | ❌ 규약을 따로 정해야 함 |
| 보안 | 없음 (네트워크 분리에 의존) | 인증서 기반 암호화·사용자 인증 내장 | TLS + 인증, 브로커가 ACL 관리 |
| 방화벽 친화성 | 인바운드 포트 열어야 함 | 인바운드 필요 (PubSub 모드 예외) | ✅ 아웃바운드 단일 연결 |
| 네트워크 단절 | 폴링 실패로 데이터 손실 | 세션 재연결 필요 | QoS·세션 유지로 복구 가능 |
| 주 사용 구간 | PLC·인버터·계측기 바로 앞 | 설비 벤더 서버 ↔ 엣지/MES | 엣지 ↔ 클라우드, 광역 |

표에서 **"데이터 모델" 행**이 디지털 트윈 관점에서 가장 중요합니다. Modbus와 MQTT는 "값을 나르는 법"만 정의하고 "값이 무엇인지"는 정의하지 않습니다. 그 공백을 누군가는 메워야 하는데, 메우지 않으면 Day 16~17에서 자산 계층과 메타데이터를 만들 때 전부 수작업이 됩니다.

## 3. Modbus — 가장 오래됐고 가장 많이 만나게 될 것

### 레지스터 네 종류

Modbus는 장치의 메모리를 네 영역으로 나눠 읽고 씁니다.

| 영역 | 크기 | 읽기/쓰기 | 전형적 용도 |
|---|---|---|---|
| Discrete Input | 1비트 | 읽기 전용 | 센서 접점, 리밋 스위치 |
| Coil | 1비트 | 읽기/쓰기 | 릴레이, 출력 ON/OFF |
| Input Register | 16비트 | 읽기 전용 | 측정값 (온도, 전류) |
| Holding Register | 16비트 | 읽기/쓰기 | 설정값, 대부분의 실측값도 여기 |

실무에서 90%는 Holding Register와 Input Register입니다. 그리고 여기서 Modbus의 가장 큰 함정이 나옵니다 — **16비트 정수밖에 없다**는 것입니다.

### 32비트 값과 바이트 순서 지옥

온도 25.6 °C를 16비트 정수로 어떻게 보낼까요? 보통 두 방법입니다.

```
방법 A — 스케일 정수
  레지스터 40001 = 256   (실제값 = 256 / 10 = 25.6 °C)
  → 스케일 팩터(÷10)를 아는 사람만 해석 가능. 문서에만 존재.

방법 B — 32비트 float를 레지스터 2개에 쪼개기
  레지스터 40001 = 0x41CC
  레지스터 40002 = 0xCCCD   → 합치면 IEEE754 float 25.6

  그런데 합치는 순서가 장치마다 다름:
    big-endian      : 41CC CCCD   ✅
    word-swapped    : CCCD 41CC   ← 같은 데이터, 다른 순서
    byte-swapped    : CC41 CDCC
```

값이 25.6이 아니라 -1.07e+8 같은 황당한 숫자로 나온다면 십중팔구 워드 순서입니다. 벤더 문서에 "Word order: High-Low"라고 적힌 한 줄이 전부이고, 그 문서가 없으면 네 조합을 전부 시도해 보는 게 정석입니다.

### 매핑 표가 곧 설계 문서

Modbus 장치를 붙이는 작업의 90%는 코드가 아니라 **매핑 표를 만드는 일**입니다. Day 06에서 만든 태그 목록에 다음 칸을 붙이면 그대로 수집 설정 파일이 됩니다.

| 태그 | 유닛ID | 주소 | 개수 | 타입 | 바이트순서 | 스케일 | 단위 | 폴링 |
|---|---|---|---|---|---|---|---|---|
| `P01.temp.die` | 1 | 40001 | 2 | float32 | word-swap | 1 | °C | 2s |
| `P01.current` | 1 | 40010 | 1 | uint16 | — | 0.1 | A | 1s |
| `P01.state.run` | 1 | 10001 | 1 | bool | — | — | — | 1s |
| `LINE1.air.flow` | 3 | 40100 | 2 | uint32 | big | 0.01 | m³ | 10s |

이 표를 YAML로 옮기면 대부분의 수집기가 그대로 먹습니다.

```yaml
devices:
  - name: press-01
    host: 192.168.10.21
    port: 502
    unit_id: 1
    poll_interval: 1s
    registers:
      - tag: P01.temp.die
        address: 40001
        type: float32
        word_order: low_high   # 벤더 문서 확인 필수
        scale: 1.0
        unit: degC
      - tag: P01.current
        address: 40010
        type: uint16
        scale: 0.1
        unit: A
```

### 폴링 설계에서 흔한 실수

Modbus는 마스터가 묻고 슬레이브가 답하는 구조입니다. 그래서 **읽는 쪽이 부하를 전적으로 결정**합니다.

- **태그마다 개별 요청을 보내는 것** — 가장 흔한 실수입니다. 40001, 40002, 40003을 따로 세 번 읽는 대신 한 번에 연속 읽기(최대 125 레지스터)로 묶으면 트래픽이 1/3로 줄어듭니다. 수집기 설정에서 "register grouping"이나 "max gap" 옵션이 이걸 자동으로 해 줍니다.
- **폴링 주기를 전부 통일하는 것** — Day 06에서 태그마다 주기를 다르게 정했던 게 여기서 살아납니다. 온도를 1초로 읽을 필요가 없는데 전부 1초로 설정하면 PLC 통신 부하가 몇 배로 뜁니다.
- **타임아웃을 너무 짧게 잡는 것** — RTU(시리얼)는 응답이 수백 ms 걸리기도 합니다. 타임아웃이 짧으면 정상 장치를 계속 "오프라인"으로 판정합니다.

> 💡 **실무 팁**: Modbus TCP에는 인증도 암호화도 없습니다. 레지스터 주소만 알면 누구나 **Coil에 쓰기**를 할 수 있고, 그건 설비를 실제로 움직인다는 뜻입니다. 수집용 계정 같은 개념이 없으므로 **네트워크 분리와 수집기의 읽기 전용 설정**이 유일한 방어선입니다. Day 37에서 OT/IT 분리를 다룰 때 다시 나옵니다.

## 4. OPC UA — 값이 아니라 모델을 가져온다

### 주소 공간이 주는 것

OPC UA가 Modbus와 결정적으로 다른 점은 서버가 **자기 자신을 설명한다**는 것입니다. 클라이언트가 접속해서 트리를 브라우징하면 이런 구조가 나옵니다.

```
Objects
└── Press_01                        (ObjectType: MachineType)
    ├── Status                      (DataType: Int32, EnumStrings 보유)
    ├── DieTemperature              (DataType: Double, EngineeringUnits: degC)
    │   ├── EURange                 (0 ~ 300)
    │   └── Historizing             (true)
    ├── MotorCurrent                (DataType: Double, EngineeringUnits: A)
    └── Methods
        └── ResetAlarm()
```

Modbus에서는 "40001이 금형 온도이고 ÷10 해야 하고 단위는 °C"라는 지식이 PDF 문서와 담당자 머릿속에만 있었습니다. OPC UA에서는 그게 **서버 안에 데이터로 들어 있습니다.** 단위, 범위, 타입, 심지어 "이 값은 저 설비에 속한다"는 계층 관계까지요.

**이게 디지털 트윈에 왜 중요한가.** Day 16에서 자산 계층 구조를, Day 17에서 메타데이터 모델(DTDL/AAS)을 만들 텐데, OPC UA 서버가 있는 설비는 그 작업의 상당 부분을 **자동 생성**할 수 있습니다. 브라우징 결과를 순회하면서 노드 트리를 그대로 자산 트리로 옮기면 되니까요. 반대로 Modbus 장치는 사람이 한 줄씩 씁니다.

### 폴링이 아니라 구독

OPC UA는 클라이언트가 Subscription을 만들고 관심 노드에 MonitoredItem을 등록하면, **값이 변할 때 서버가 보내줍니다.**

```python
# python-opcua 계열 라이브러리의 전형적 형태
class Handler:
    def datachange_notification(self, node, val, data):
        print(node, val, data.monitored_item.Value.SourceTimestamp)

sub = client.create_subscription(500, Handler())   # 500ms publishing interval
sub.subscribe_data_change([
    client.get_node("ns=2;s=Press_01.DieTemperature"),
    client.get_node("ns=2;s=Press_01.MotorCurrent"),
])
```

여기서 두 개의 숫자를 구분해야 합니다.

| 설정 | 뜻 | 효과 |
|---|---|---|
| Publishing Interval | 서버가 쌓인 변경분을 묶어 보내는 주기 (예: 500 ms) | 네트워크 패킷 수를 결정 |
| Sampling Interval | 서버가 내부적으로 값을 확인하는 주기 (예: 100 ms) | 놓치는 변화량을 결정 |
| Deadband | 이만큼 변해야 보고 (예: 0.5 °C) | 노이즈로 인한 불필요한 전송 차단 |

Deadband는 특히 유용합니다. 온도가 ±0.05 °C로 흔들릴 때마다 메시지를 받을 이유가 없습니다. Day 11의 엣지 전처리에서 할 일을 서버가 미리 해 주는 셈입니다.

### 그리고 타임스탬프

OPC UA는 값 하나에 **두 개의 시각**을 붙여 보냅니다.

- `SourceTimestamp` — 그 값이 실제로 만들어진 시각 (설비 쪽)
- `ServerTimestamp` — 서버가 그 값을 처리한 시각

디지털 트윈에서는 **SourceTimestamp를 저장해야 합니다.** 네트워크 지연이나 수집기 지연이 섞인 시각으로 저장하면, Day 28의 리플레이에서 사건 순서가 뒤바뀌고 Day 30의 진동·전류 상관 분석이 어긋납니다. Modbus에는 타임스탬프 개념 자체가 없어서 **수집기가 읽은 시각**을 쓸 수밖에 없는데, 이것이 두 프로토콜의 데이터 품질 차이를 가장 극명하게 보여주는 지점입니다.

### 대가: 복잡성

OPC UA의 단점도 분명합니다. 인증서 교환(클라이언트와 서버가 서로의 인증서를 신뢰 목록에 넣어야 함), 보안 정책 협상, 세션 관리까지 붙으면 첫 연결에 하루가 걸리기도 합니다. "포트 502에 TCP 소켓 열면 끝"인 Modbus와는 다른 세계입니다. Day 09에서 이 과정을 실제로 밟아 볼 예정입니다.

## 5. MQTT — 공장 밖으로 나가는 유일한 길

### 왜 발행/구독인가

Modbus와 OPC UA는 모두 **묻는 쪽이 대상의 주소를 알아야** 합니다. 클라우드에서 공장 안 PLC를 직접 폴링하려면 방화벽에 인바운드 구멍을 뚫어야 하는데, 이건 보안팀이 절대 승인하지 않습니다.

MQTT는 반대 방향으로 풉니다. **엣지 게이트웨이가 브로커로 아웃바운드 연결을 열고**, 그 연결 위로 데이터를 밀어 올립니다. 방화벽 입장에서는 평범한 아웃바운드 TLS 연결 하나입니다. 이것 하나만으로도 MQTT가 IoT의 사실상 표준이 된 이유가 설명됩니다.

### QoS를 제대로 고르기

| QoS | 보장 | 비용 | 트윈에서 쓸 자리 |
|---|---|---|---|
| 0 — At most once | 못 받을 수 있음 | 가장 가벼움 | 고주기 센서값 (어차피 다음 값이 곧 온다) |
| 1 — At least once | 반드시 받지만 중복 가능 | 중간 | 경보, 상태 변화, 적산값 |
| 2 — Exactly once | 정확히 한 번 | 가장 무거움 | 과금·법적 기록처럼 중복이 치명적인 경우 |

**QoS 2를 기본값으로 쓰는 것은 거의 언제나 과설계입니다.** 실무에서는 QoS 1 + 수신 측 멱등 처리(같은 태그·같은 타임스탬프면 덮어쓰기) 조합이 압도적으로 흔합니다. 시계열 DB는 대부분 (측정값, 태그, 시각) 조합에 쓰기를 하면 중복이 자연스럽게 흡수되므로, QoS 1의 중복은 사실상 공짜로 해결됩니다.

### Retained와 LWT — 트윈 화면이 비지 않게 하는 두 장치

트윈 대시보드를 새로 열었을 때 **모든 게이지가 비어 있는** 문제, MQTT에서는 두 기능으로 해결합니다.

- **Retained 메시지**: 브로커가 토픽별 마지막 값을 보관합니다. 신규 구독자가 붙는 즉시 최신값을 받으므로 화면이 바로 채워집니다. 단, 1초짜리 고주기 센서에 retain을 걸면 브로커 메모리를 잡아먹으니 **상태값·설정값에만** 씁니다.
- **LWT(Last Will and Testament)**: 클라이언트가 접속할 때 "내가 갑자기 끊기면 이 토픽에 이 메시지를 대신 발행해 달라"고 브로커에 맡겨둡니다. 엣지 게이트웨이가 죽으면 브로커가 `factory/line1/edge-01/status = offline`을 자동 발행합니다.

LWT는 Day 06 5절에서 이야기한 **flatline 문제의 정답**입니다. 센서 값이 그대로 멈춰 있을 때 "설비가 안정적인 것"과 "게이트웨이가 죽은 것"을 구분할 방법이 없었는데, LWT가 있으면 트윈이 그 설비를 명확히 회색 처리할 수 있습니다.

```
연결 시 등록:
  LWT topic   : factory/line1/edge-01/status
  LWT payload : {"state":"offline"}
  LWT retain  : true
  LWT QoS     : 1

정상 접속 직후 직접 발행:
  factory/line1/edge-01/status = {"state":"online"}  (retain=true)
```

### 토픽 설계가 곧 자산 계층

MQTT에는 데이터 모델이 없다고 했습니다. 그 공백을 메우는 게 **토픽 네이밍 규약**입니다.

```
factory/{site}/{line}/{asset}/{measure}

factory/suwon/line1/press-01/temp.die
factory/suwon/line1/press-01/current
factory/suwon/line1/press-01/state
factory/suwon/line1/_edge/edge-01/status
```

좋은 토픽 구조는 세 가지를 만족합니다.

1. **왼쪽이 넓고 오른쪽이 좁다** — 와일드카드 구독이 자연스럽게 됩니다. `factory/suwon/line1/+/temp.die`로 라인 전체 온도를 한 번에 받습니다.
2. **토픽에는 식별자만, 값에는 데이터만** — 토픽에 `temp_25.6` 같은 값을 넣지 않습니다.
3. **Day 16의 자산 계층과 같은 구조** — 토픽 트리와 3D 씬의 노드 트리가 같은 경로를 쓰면, Unity에서 수신한 토픽 문자열로 바로 대상 오브젝트를 찾을 수 있습니다. Day 19~20에서 이 구조 덕을 크게 봅니다.

페이로드는 JSON이 무난한 출발점입니다.

```json
{
  "ts": "2026-11-18T09:14:32.120Z",
  "v": 182.4,
  "u": "degC",
  "q": "good"
}
```

`ts`에 **원천 타임스탬프**를 넣는 것, `q`로 품질 플래그를 함께 보내는 것 — 둘 다 Day 06 5절의 "센서를 믿지 않는 설계"를 프로토콜 수준에서 구현한 것입니다. 대역폭이 문제가 되면 나중에 MessagePack이나 Protobuf로 바꾸면 되지만, 그건 측정해 보고 결정할 일입니다.

> 💡 **실무 팁**: 토픽 이름은 한번 굳으면 바꾸기가 매우 어렵습니다. 구독하는 모든 쪽(시계열 DB 수집기, 대시보드, Unity 트윈, 경보 엔진)이 전부 영향을 받기 때문입니다. **첫 토픽을 발행하기 전에 규약 문서를 한 장 써 두세요.** 들이는 시간 대비 가장 수익률이 좋은 30분입니다.

## 6. Day 06 표에 경로 칸 채우기

세 프로토콜을 정리했으니, Day 06 인벤토리 표에 "이 태그가 어떤 길로 오는가"를 덧붙입니다.

| 태그 | 원천 | 현장 구간 | 상위 구간 | 타임스탬프 | 비고 |
|---|---|---|---|---|---|
| `P01.temp.die` | PLC (Modbus TCP) | Modbus 2s 폴링 | MQTT QoS 0 | 수집기 시각 | float32 워드순서 확인 필요 |
| `P01.vib.rms` | 진동 센서 모듈 | OPC UA 구독 (deadband 0.2) | MQTT QoS 0 | SourceTimestamp | 원파형은 엣지에 보관 |
| `P01.current` | CT → PLC | Modbus 1s 폴링 | MQTT QoS 0 | 수집기 시각 | uint16 ÷10 |
| `P01.alarm.*` | PLC 접점 | Modbus 1s 폴링 | MQTT **QoS 1, retain** | 수집기 시각 | 놓치면 안 되는 이벤트 |
| `LINE1.air.flow` | 유량계 | Modbus 10s 폴링 | MQTT **QoS 1** | 수집기 시각 | 적산값, 중복 무해 |
| `edge-01.status` | 게이트웨이 | — | MQTT **LWT, retain** | 브로커 시각 | 연결 감시 |

표에서 읽어야 할 것 두 가지입니다.

**첫째, 대부분의 태그가 두 구간을 거칩니다.** "Modbus냐 MQTT냐"가 아니라 "Modbus로 받아서 MQTT로 올린다"가 정상입니다. 엣지 게이트웨이는 그 사이에서 **프로토콜 변환기**로 일합니다. Day 11에서 다룰 역할의 절반이 이것입니다.

**둘째, 타임스탬프 칸이 태그마다 다릅니다.** OPC UA 태그만 원천 시각을 갖고 나머지는 수집기 시각입니다. 즉 **같은 트윈 안에 정밀도가 다른 시간축이 섞여 있다**는 뜻이고, 이걸 모르면 Day 28에서 리플레이를 만들 때 "진동 이상이 전류 상승보다 먼저였나 나중이었나" 같은 질문에 잘못된 답을 하게 됩니다. 수집기 시각을 쓰는 태그는 폴링 주기만큼의 불확실성을 항상 달고 다닙니다.

### 신규 설비라면 달라지는가

"그린필드면 전부 OPC UA로 통일하면 되지 않나" — 부분적으로는 맞습니다. 최신 설비는 대개 OPC UA 서버를 내장하고 있고, 그 경우 현장 구간은 훨씬 깔끔해집니다. 하지만 상위 구간은 여전히 MQTT인 경우가 많습니다. 수백 개 사이트를 클라우드 한 곳으로 모을 때 아웃바운드 발행/구독의 운영 편의가 압도적이기 때문입니다. OPC UA도 PubSub 모드로 MQTT 위에 얹을 수 있어서, 최근에는 **"OPC UA 정보 모델 + MQTT 전송"** 조합이 늘고 있습니다. 두 세계가 만나는 지점이라고 보면 됩니다.

## 📝 핵심 요약

1. 한 현장에 세 프로토콜이 공존하는 게 정상이다. Modbus는 PLC 바로 앞, OPC UA는 설비 서버와 엣지 사이, MQTT는 공장 밖으로 나가는 구간을 맡는다.
2. Modbus는 16비트 레지스터만 있고 의미가 없다. 32비트 값의 워드 순서와 스케일 팩터를 담은 **매핑 표가 곧 설계 문서**이며, 연속 읽기 묶음과 태그별 폴링 주기 분리가 성능을 좌우한다.
3. OPC UA는 서버가 타입·단위·계층을 스스로 설명한다. 그래서 Day 16~17의 자산 모델을 상당 부분 자동 생성할 수 있고, 무엇보다 **SourceTimestamp**라는 원천 시각을 제공한다.
4. MQTT는 아웃바운드 단일 연결로 방화벽을 통과한다. QoS는 1 + 수신 측 멱등 처리가 실무 기본값이고, Retained는 화면 초기화를, LWT는 게이트웨이 사망 감지를 해결한다.
5. 토픽 네이밍은 MQTT에 없는 데이터 모델을 대신한다. Day 16의 자산 계층·3D 노드 트리와 같은 경로 구조로 설계해 두면 Unity 바인딩이 훨씬 수월해진다.
